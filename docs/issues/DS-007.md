# DS-007 — Add progress indicators and skeletons

Status: Resolved · 2026-11-06

## Problem

Application essentials need determinate/unknown progress and content placeholders.
Invalid ranges must not produce invalid geometry or misleading accessibility
values. Loading animations need reduced-motion and clipping behavior, with one
meaningful loading announcement instead of many decorative stops.

## Remediation

Implement token-based sharp progress tracks with sizes, fill variants, labels,
percentages, custom maxima, and explicit indeterminate state. Add five skeleton
shapes, a named busy group, and card/list/content/table compositions. Keep real
loading work, values, completion, and replacement content in the application.
Test ranges, identity, accessibility, layouts, and animation scheduling; review
rendering at multiple scales and themes plus native behavior.

## Resolution

Implemented on `ticket/progress-skeletons` (1.0.3), without new dependencies.
Progress supplies three sizes/four fills, custom ranges, wrapping labels,
right-aligned values, and an unknown state with no numeric completion. Five
skeleton shapes and four compositions use a named busy group with decorative
children hidden from accessibility. Shared motion respects visibility, pause,
and reduced motion. The host owns completion and replacement content.

All 55 integration tests and one doctest pass, including invalid ranges, stable
IDs, focus preservation, animation scheduling/pixel changes, narrow bounds, and
the example's reserved-height replacement. All required Clippy configurations
pass. Light/dark WGPU baselines at 1x/1.5x/2x and native macOS values/loading
regions were inspected. See the [guide](../progress-skeletons.md).

The pulse uses the live CSS's two-second period with cosine easing; templates
remain inline placeholders, without virtualized/data behavior. Running screen
reader, Windows/Linux GUI, and minimum-toolchain testing remain outstanding.
Source-palette contrast limitations remain in DS-003.
