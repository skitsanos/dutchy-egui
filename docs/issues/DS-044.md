# DS-044 — Theme style was installed for one egui theme only

Status: Resolved · 2026-11-07

## Problem

`Theme::apply` set the egui theme preference and then installed the Dutchy
style through `set_global_style`, which writes only the slot of the theme that
is active at that moment. If the preference changed later, for example a host
following the system theme or a test harness that calls `set_theme` after the
context setup, native egui widgets fell back to egui's default style for the
other theme: default fonts and sizes, 20-point controls, and the dark default
text color (gray 215) for editors. Dutchy-painted widgets hid the problem
because they read the palette directly. Many rendering tests ran in exactly
this state, so their baselines captured egui-default native widgets, and the
muted editor text inside accordion bodies (DS-037) went unnoticed.

## Remediation

Install the style for both egui themes with `set_style_of`, because `Mode`
already decides the palette; keep the preference set so native theme-aware
behavior matches the mode.

## Resolution

Fixed in 1.0.16 in `src/theme.rs`. Six baselines that had captured egui-default
native widgets were refreshed after visual review (`disclosure-*`,
`accordion-keyboard-focus`, `tab-roving-focus`, `stepper-navigation-hover`);
the only visible change is foreground editor text where it was muted or egui's
default grey. Two tests whose fixture geometry assumed 20-point native
controls were adjusted: the lightbox backdrop test now presses the viewport
gutter explicitly, and the sticky-header test exposed and now covers the
header-focus scroll defect recorded in DS-038.
