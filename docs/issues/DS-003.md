# DS-003 — Source status fills have limited white-text contrast

Status: Resolved · 2026-11-07

## Problem

The source uses white labels on orange and several semantic fills. Relative
sRGB luminance calculations give approximately 2.79:1 for Orange, 2.13:1 for
Warning, 3.33:1 for Success, and 3.78:1 for Destructive. These do not reach
4.5:1 for ordinary small text. Blanket accessibility claims in older source
documentation therefore cannot be carried into this library.

## Remediation

Preserve the requested source appearance during the visual proof. Expose
`Palette::on_primary` and `Palette::on_status` so host applications can select
appropriate foreground/fill pairs. Document the limitation in the README and
reference contract. A future design decision can introduce per-status text
tokens or adjust fills, with updated rendering baselines.

## Resolution

Closed as a design decision on 2026-11-07, together with DS-027: the library
keeps the design system's white labels on the orange and semantic fills even
though the ratios above stay below 4.5:1. The ratios were calculated from the
exact rounded sRGB token bytes, without alpha compositing, and the ledger
verification audit (DS-028) reproduced them from the live reference's computed
colors, so the limitation is inherited rather than introduced. The
implementation makes no blanket contrast compliance claim and does not
silently change brand or status colors; the README and the reference contract
record the limitation beside DS-027.

Applications that need stricter ratios tune the pairs on their side. `Palette`
fields are public, so a host sets `on_primary` and `on_status` to a dark
foreground, or adjusts the fills themselves, on its `Theme` before
`dutchy_egui::install`. Widgets read the tokens at paint time: `on_status`
reaches buttons, badges, alerts, toasts and menus, and `on_primary` reaches
every primary-filled control. No per-status text tokens are added and no
baselines change.
