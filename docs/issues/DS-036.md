# DS-036 — Accordion and tab details, and the focus-visible policy as documented

Status: Resolved · 2026-11-07

## Problem

Low-severity gaps against the live `Accordion` and `Tabs` components and the
shared focus policy, none recorded in `docs/accordions-tabs.md`:

- Bordered accordion headers use 0.05 em tracking
  (`src/widgets/accordion/paint.rs`); the live bordered summary uses 0.025 em
  and only the default variant uses 0.05 em.
- The web lights the accent edge when any part of an open item is hovered;
  the port keys the edge to the header response only
  (`src/widgets/accordion/mod.rs`).
- With a tab's close button focused, Left/Right are not locked
  (`lock_arrows` is applied to tab responses only in `src/widgets/tabs/bar.rs`),
  so they fall through to egui's spatial navigation instead of roving along
  the strip; Up/Down leave a focused tab the same way.
- The tab close glyph is an 8-point X with a 2-point stroke against the web's
  roughly 6-point visible path, and underline labels are centered in the full
  56-point rect rather than above the 4-point underline, so they sit about
  2 points lower than the web (`src/widgets/tabs/paint.rs`).
- The overflow strip keeps egui's floating scrollbar, which can overlay the
  2-point baseline and 4-point underline on hover; the web hides its scrollbar.
- `src/interaction.rs` states that programmatic focus defaults to a visible
  cue. That holds only until the first pointer press, because the input mode
  persists in temporary memory; later programmatic focus, including the
  restoration after a pointer-closed tab, paints no ring until a key or
  assistive event arrives. The guide's statement that egui memory holds only
  transient focus, scroll, and animation data omits this global flag and the
  per-strip previous-focus list.
- The mode scan recognises `Key`, `PointerButton`, and AccessKit action events
  only; `Text`, `Ime`, and clipboard events do not restore keyboard mode after
  a pointer press.

The DS-011 decision that a selected tab shows its active mark alone means a
keyboard user entering a strip on the selected tab sees no change. WCAG 2.4.7
expects a visible focus indicator on every focusable item; this is recorded
here as a consequence of that decision, not as a defect.

## Remediation

Use `Tracking::Wide` for bordered headers, extend the accent-edge hover to the
open body, lock arrows on the close button, align the label baseline and glyph
with the web if parity matters, consider a solid scrollbar style for the strip,
correct the focus-policy comment and guide, and optionally treat text, IME,
and clipboard events as keyboard input. If the selected-tab decision stands,
note the WCAG implication in `docs/reference.md`.

## Resolution

Resolved in 1.0.16. Bordered accordion headers use `Tracking::Wide`; the
default accent edge lights while the header or the open body is under the
pointer (`tests/accordions.rs`). Left/Right are locked on a focused tab close
button (`tests/tabs.rs`). Text, IME, paste, copy and cut events restore the
keyboard input mode (`tests/focus.rs`), and the `focus_is_visible` comment,
`docs/reference.md` and `docs/accordions-tabs.md` describe the persisted
input-mode flag and the per-strip focus record. The WCAG 2.4.7 consequence of
the DS-011 selected-tab decision is recorded in `docs/reference.md`. The close
glyph size, the label baseline and the floating overflow scrollbar remain as
recorded differences. The disclosure baselines were refreshed.
