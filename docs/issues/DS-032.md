# DS-032 — Accessible names carry the visual uppercase transform

Status: Resolved · 2026-11-07

## Problem

The web applies uppercase with CSS `text-transform`, so assistive technology
receives the original text. The port uppercases the string itself and exposes
that string as the accessible name: `Button` hands egui an uppercased layout
job, and egui names the button from the galley text; tabs, accordion headers,
breadcrumb items, card titles, and empty-state headings call `to_uppercase()`
before `WidgetInfo::labeled` or `set_label` (`src/widgets/tabs/paint.rs`,
`accordion/paint.rs`, `breadcrumbs/paint.rs`, `card/mod.rs`,
`empty_state/mod.rs`). Screen readers may spell out short all-caps words as
initialisms, and the names no longer match the host's own strings, which also
leaks into tests that query "APPLY RECORD" or "LIBRARY".

## Remediation

Keep the visual transform but name widgets from the original label: call
`response.widget_info` after `ui.add` for `Button`, and pass the untransformed
label to `WidgetInfo::labeled`/`set_label` elsewhere. Update the tests that
locate controls by uppercased names. `Text::uppercase` used as plain content is
unaffected; the Unicode conversion remains the documented behavior.

## Resolution

Fixed in 1.0.16. `Button` names itself from the host label through
`accessible_name`; tabs, accordion headers, breadcrumbs, card titles, and
empty-state headings pass the untransformed label; `Badge` names itself from
its label; and uppercase `Text` (including field labels) sets both the node
label and value to the text as written, because AccessKit derives a label
node's name from its value. `tests/accessible_names.rs` asserts original-case
names across these controls, and the existing suites now query original-case
names. Visible rendering is unchanged.
