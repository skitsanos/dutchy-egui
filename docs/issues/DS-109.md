# DS-109 — TreeView over the List row engine

Status: Resolved in 1.2.0 · 2026-11-10

## Problem

Workbench applications need hierarchical navigation without rebuilding List's
selection, focus and virtualization or losing hidden selection on collapse.
Flattened rows also need genuine tree parenting and sibling metadata for
assistive technology.

## Remediation

Add keyed, host-owned expansion with Left/Right and disclosure controls.
Extend List internally for indented tree rows, retained hidden selection and
virtualized ancestor/group accessibility. Keep the public List API compatible,
preserve the text-click fix, add a large showcase and document supported scope.

## Resolution

TreeView now shares List's keyed rows, selection, type-ahead, roving focus and
fixed-height virtualization. Collapsing retains hidden selection and nested
expansion; hidden focus returns to the nearest visible ancestor. TreeItem levels,
sibling groups and expansion actions remain available when ancestors scroll away.

A review before release found tree levels one too high: AccessKit levels are
zero-based and its Windows adapter adds one, so root items reported level 2.
Levels now equal depth, the semantics test checks the root and a nested item,
and the baselines include a closed branch.

All 23 local gates passed: 691 all-feature tests, 451 minimal tests, three Clippy
profiles, strict documentation, semver against published 1.1.0, WASM, MSRV 1.95,
feature combinations, native examples and actual archive inspection. Seventeen
TreeView tests cover hierarchy, input, lifecycle and rendering at light 1×, dark
1.5× and blue 2×; existing List regressions remain green. Before the review,
native macOS checks verified arrows, disclosure/text clicks, activation, one Tab
stop and reveal among 10,000 documents. No VoiceOver session was performed.

See [the guide](../tree-view.md) for scope: passive fixed-height rows, no lazy
loading or drag/reorder.
