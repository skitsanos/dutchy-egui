# DS-076 — Opening an application menu shifts following content

Status: Resolved in 1.0.26 · 2026-11-09

## Problem

The supplied closed/open screenshots show a larger gap between MenuBar and
Toolbar after opening File. Popup overlays must not consume host layout space
or move sibling content. The same attachment path is used by Toolbar menus and
context menus on existing controls.

## Remediation

Reproduce with geometry assertions across open/switch/close transitions and
trace existing-response attachment through Dropdown. Remove any redundant
allocation while preserving trigger identity, host-owned enabled state,
keyboard routing and accessibility. Verify composed controls, narrow layouts,
themes/scales and native rendering, then run the required checks.

## Resolution

Reproduced an 8-point increase in MenuBar's layout height and cursor position:
an empty trigger scope allocated item spacing when reusing an existing
Response. Only newly drawn triggers now allocate a scope; existing-response
and context attachments do not advance host layout.

Two new regression tests pass across opening/switching/closing, nested
MenuBar/Toolbar composition, narrow layouts, themes/scales, direct cursor
invariants and host-enabled state. All 14 automated gates pass: 517 all-feature
and 366 minimal tests, all Clippy profiles, docs, WASM, partial features, MSRV
and native build. The actual archive builds and passes inspection.

Native light/dark captures retain menu bar, toolbar and canvas positions;
opening, switching and Toolbar overlays do not shift content. Nested Tab
directions remain correct. Only nine intended rich-menu baselines changed;
119 earlier baselines and 779 protected files remain unchanged. The evidence
covers macOS and headless checks, not other platforms or screen readers.
No release, commit or push was performed; version remains 1.0.25.
