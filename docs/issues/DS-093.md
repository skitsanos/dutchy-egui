# DS-093 — Bare activation keys can be bound and then swallowed everywhere

Status: Resolved in 1.0.28 (found in its review) · Priority: P2 · 2026-11-09

## Problem

KeyRecorder accepts an unmodified Enter, Space, arrow, Home, End or Page key.
Once such a chord is an application-scope binding, `CommandRegistry::dispatch`
consumes it before controls draw. A focused button, row or list then no longer
responds to its native activation or navigation key, outside text editors and
overlays. The Todo and Canal Studio shortcut settings expose this to end users,
and the reserved list only covers other commands' bindings.

A scratch probe showed it directly. With no binding, Enter on a Tab-focused
egui button clicks it. With a command bound to bare Enter, the same key press
fires the command and the button receives no click.

## Remediation

Reject unmodified activation and navigation keys in KeyRecorder by default,
alongside Tab and Escape, with an explicit host opt-in for applications that
want them. Alternatively, have application-scope dispatch leave those keys to
a focused non-text widget. Document the reserved set in the command guide and
add interaction regressions for the recorder and for dispatch.

## Resolution

Registry dispatch leaves unmodified Enter, Space, Tab, Escape, arrow, Home,
End and page keys to a focused control. An application binding on them applies
only while nothing has focus. KeyRecorder rejects those keys without Command,
Control or Alt, showing a "Key needs a modifier" alert, unless the host calls
`allow_navigation_keys(true)`. New regressions show a focused button keeping
Enter and arrows while a modified chord still dispatches. The recorder rejects
bare Enter, Space, ArrowDown, PageUp and Shift+Home and accepts Alt+ArrowDown.
The discarded-pass Enter test now opts in explicitly. See the
[review record](../verification-review-1.0.28.md).
Included in the [1.0.28 release qualification](../verification-release-1.0.28.md).
