# DS-026 — Scribble focus repeatedly overrides manual scrolling

Status: Resolved · 2026-11-07

## Problem

After drawing in the showcase, scrolling toward the read-only copy snapped back
to the editable canvas. Focused toolbar controls and the read-only canvas could
also keep their region in view indefinitely. Both canvas and toolbar requested
scrolling every frame while focused, competing with wheel/scrollbar input.
The empty read-only view additionally said “Draw here.”

## Remediation

Reveal a canvas when it gains focus or receives a handled drawing command, and
reveal toolbar controls when focus changes or an action is activated. Retaining
focus alone does not request scrolling. Avoid moving an active pointer gesture.

Keep keyboard drafts in logical drawing coordinates when the canvas moves during
reveal/scroll/layout; pointer drafts still cancel when their screen rectangle
changes. Default empty read-only text becomes “No drawing,” while explicit
placeholder overrides remain supported.

Add focused scroll-area regressions for editable-canvas focus, toolbar focus,
read-only reveal/scroll-away, and keyboard drawing after scrolling out of view.

## Resolution

Fixed locally for 1.0.15 on 2026-11-07. All four regressions failed before the fix
and pass afterward. Native macOS Glow verification reproduced the original
snap-back after a pointer stroke. The corrected build reaches the read-only
canvas while editor/toolbar focus is retained, scrolls away while read-only
retains focus, and reveals it once when reached through Tab navigation.
Space/arrows/Enter after scrolling away reveal the editor and commit a complete
keyboard stroke; completed drawing data stays shared with the read-only view.
The empty read-only hint was also checked visually.

No new dependency or version/main push is involved. Required project checks,
feature coverage, rendering baselines and package checks passed. Physical
touch/pen and other GUI platform acceptance remain separate from the native
pointer/keyboard evidence.
