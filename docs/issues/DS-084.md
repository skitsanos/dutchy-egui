# DS-084 — Menu triggers kept Escape and menu-bar entries reported two roles

Status: Resolved locally (Unreleased) · Priority: P3 · 2026-11-09

## Problem

The independent review of the richer-menu work (DS-073 to DS-076) left four
smaller observations without tickets. Two changed behavior:

- MenuBar entries and Toolbar menu buttons locked Escape for themselves, so
  Escape on a closed trigger kept focus, while every plain Toolbar tool and
  every other egui widget releases it. One Toolbar therefore answered Escape
  two ways.
- MenuBar entries registered their widget information twice per frame, first
  as a Button through the shared action core and then as a MenuItem. On a
  click frame egui emitted two `Clicked` output events, the first with the
  wrong role.

Two were redundant code: a submenu popup re-anchored to the widget its
response already anchors, and the dropdown assigned its item list twice.
Several documented behaviors had no test: Up opening a MenuBar or Toolbar menu
at its last entry, an icon-only menu button keeping the square tool target,
and the pointer path that crosses a sibling on its way to an open child.

## Remediation

Lock only arrow keys on triggers and keep the Escape lock on menu rows, where
Escape closes one level. Give the shared action core an explicit accessibility
role so each control registers once with the right role. Remove the two
redundancies. Add tests for each case, failing first where behavior changes.

## Resolution

The escape lock is now a parameter: rows keep it, MenuBar entries and Toolbar
menu buttons pass none, so Escape releases a closed trigger like other egui
widgets. An open menu still closes on Escape and returns focus to its trigger.
`core::Action` carries a role; IconButton, ToggleButton and Toolbar items pass
Button, MenuBar passes MenuItem and its second registration is gone. The
anchor and item-list duplicates are removed.

New tests: `escape_treats_menu_buttons_like_the_other_tools`,
`up_opens_a_toolbar_menu_at_its_last_entry` and
`icon_only_menu_buttons_keep_the_square_tool_target` in
`tests/toolbar_menus.rs`; `bar_entries_report_one_menu_item_event_per_click`,
`escape_on_a_closed_bar_entry_releases_focus_like_other_widgets` and
`up_opens_a_bar_menu_at_its_last_entry` in `tests/menu_bar.rs`; and
`a_diagonal_pointer_path_across_a_sibling_keeps_the_open_child` in
`tests/menu_polish.rs`. The three Escape and event tests failed before the
change (focus kept; two click events) and pass after it; the coverage tests
pass on the existing behavior. The diagonal test steps the harness at 60 frames
per second, because kittest's default quarter-second step leaves no samples
inside egui's 0.1-second pointer history and pointer direction then always
reads zero. After the change, `cargo fmt --all --check`, 527 all-feature and
376 minimal-feature tests, all three Clippy configurations, strict rustdoc,
both WASM checks, the 1.95 MSRV check and the showcase build pass on
2026-11-09, and no rendering baseline changed. Native behavior was not
re-checked.

Not changed: the widget output events of Dutchy `Button` carry its uppercase
display text, while its AccessKit name keeps the host's casing. `Button` wraps
egui's native button, which reports its visible text before Dutchy sets the
name; changing that would mean replacing the native control. AccessKit, which
screen readers use, is unaffected; only egui's own speech output differs.
