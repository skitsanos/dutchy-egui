# DS-065 — Showcase keeps the scroll offset across pages

Status: Resolved in 1.0.24 · 2026-11-08

## Problem

The showcase content uses one `ScrollArea` with the fixed salt
`showcase-content`, so the vertical offset survives page changes. After
scrolling the Color picker page and choosing Icon buttons, the new page opened
about 400 points down with its heading hidden (native macOS, 2026-11-08).
Visitors reading one page then land mid-way into every following page until
they scroll back.

Page kickers also mix group names for the port additions: Icon buttons, Toggle
buttons and Toolbars say "Native components", Media cards and Search input say
"Native additions", and the Color picker says "Application essentials", although
`docs/coverage.md` lists all five as port additions.

## Remediation

Salt the content scroll area with the current page, or reset its offset when the
page changes, keeping the sidebar focus-reveal behavior. Add a showcase test that
scrolls one page, switches pages and asserts that the new heading is visible at
the top. Use one kicker group name for the port additions that matches the
coverage matrix.

## Resolution

The showcase content `ScrollArea` is salted with the current `Page` (now `Hash`),
so every page keeps its own offset: a newly opened page starts at the top and
returning to a scrolled page restores its position. The regression
`switching_pages_opens_the_new_page_at_the_top` (`tests/rendering.rs`) scrolls
the Color picker page with wheel events and asserts that the Icon buttons heading
then opens at the original heading position; it failed before the change. The
Color picker, Form controls, Media cards, Search input, Icon buttons, Toggle
buttons and Toolbars pages now share the "Native additions" kicker. No tracked
baseline captures those kickers, so none changed. Evidence for
the original defect: the fixed `showcase-content` salt in
`examples/showcase/gallery/mod.rs` and the native observation on 2026-11-08.
