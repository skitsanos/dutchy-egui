# Project instructions

- Always communicate in English.
- Build Dutchy as an idiomatic egui library. Keep application state in the host.
- The web system is the visual reference, not a component inventory limit. Add useful native Rust controls and developer-facing polish; document their supported scope and remaining limits.
- Use the most recent stable crate releases; verify versions when adding or upgrading them.
- Keep runtime dependencies minimal. Prefer small, maintained-in-repository implementations over widget/helper crates. MIT-licensed ideas/code may be adapted with attribution and license notices; preserve all applicable notices.
- Prefer low cognitive complexity, focused functions, and composition. Clippy's cognitive-complexity threshold is 15. Treat 400 lines per code file as a soft cap; split by responsibility before growing a large file.
- All colors, typography, control sizes, spacing, borders, and motion come from shared tokens. Zero corner radius, flat fills, no gradients or blurred shadows.
- Preserve native egui interaction and accessibility behavior. Custom painting must include accessible names/roles and keyboard behavior where applicable.
- Keep `docs/` lean: guides, reference decisions, the versioning policy and the Issues Ledger. Do not commit per-change plans, verification reports, review records or receipts. Plans live in the conversation until the work lands; durable decisions go into a guide, `docs/reference.md` or a ledger entry.
- Keep README essential: purpose, minimal setup, showcase command and documentation/license links. Component and development guides belong in docs/; version history belongs in CHANGELOG.md.
- `docs/issues/` is the Issues Ledger. Use sequential `DS-{number}.md` files with `Problem`, `Remediation`, and `Resolution` sections. Keep entries readable, usually under 400 words; state evidence in a sentence or two in the Resolution and leave unresolved limitations explicit.
- Versioning starts at **1.0.0**. Every push to `main` must advance the package version relative to the last pushed version (at least a patch), update `Cargo.lock` and `CHANGELOG.md`, and pass checks. `docs/versioning.md` decides whether the patch, minor or major number advances, and which public types must be `#[non_exhaustive]`. The initial published/pushed baseline is 1.0.0. Never push without user authorization.
- After every push, clean repository-local generated artifacts, stale worktree metadata, obsolete clean worktrees, and unused merged branches. Inspect before deleting; preserve the active checkout, dirty/unmerged work, tracked assets/snapshots, and work in use. Subagents may perform this cleanup. Close superseded task-owned previews before removing their outputs; preserve unrelated processes. Report the outcome and any preserved work in the hand-off, not in repository files.
- Keep bundled font licenses and third-party notices in the distributed package.
- Before a release push, inspect the actual crate archive against approved repository paths, excluding media, storyboard outputs and generated snapshot differences. Keep commit and push steps separate from qualification so a failed gate stops delivery. Summarize the gate results in the release commit message.
- Run required checks after Rust changes, and fix failures before completion:
  - `cargo fmt --all --check`
  - `cargo test --all-features`
  - `cargo clippy --all-targets -- -D warnings`
  - `cargo clippy --all-targets --all-features -- -D warnings`
  - `cargo clippy --all-targets --no-default-features -- -D warnings`
- Verify the renderer at multiple display scales and themes. Use meaningful interaction tests and focused rendering checks; do not claim browser/native parity from compilation alone.
